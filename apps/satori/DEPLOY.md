# Satori Deployment Guide

**Canonical Service Name:** `satori` | **Service ID:** `srv-d9pmh96417fc73e88po0` | **URL:** `satori-agenda.onrender.com`
> **WARNING**: This file is checked into version control. It must **never** contain real credentials, database URLs, or password hashes. Use only the exact placeholder formats provided below.

## Pre-Deploy Preparation

Before committing credentials locally, ensure the repository's credential guard is active:
```bash
git config core.hooksPath .githooks
```

Before configuring Render, build the container locally with the current Git commit hash baked into the image. This guarantees `/health` responds with the actual revision being served instead of "unknown".
```bash
docker build --build-arg GIT_SHA=$(git rev-parse --short HEAD) -t satori .
```

## Render Dashboard Configuration

When you connect this repository to Render via the Blueprint (`render.yaml`), it will create the `satori-agenda` web service but will **not** automatically deploy (`autoDeploy: false`). Before you click "Manual Deploy", you must configure the following four environment variables that were intentionally excluded from source control (`sync: false`):

1. **`TURSO_DATABASE_URL`**
   - **Source:** Run `turso db show satori --url` on your machine.
   - **Value:** e.g., `libsql://<your-db>-<your-org>.turso.io`

2. **`TURSO_AUTH_TOKEN`**
   - **Source:** Generate a fresh, dedicated token by running `turso db tokens create satori`. (Do not reuse local tokens).
   - **Value:** The JWT token granting access to the Turso database (e.g., `eyJ<jwt>`).

3. **`PORTAL_PASSWORD_HASH`**
   - **Source:** Run `npx tsx scripts/hashPassword.ts <your_production_password>`.
   - **Value:** The bcrypt hash string (e.g., `$2b$12$<bcrypt-hash>`).

4. **`CALENDAR_ICS_URL`** (and optional **`FAMILY_CALENDAR_ICS_URL`**)
   - **Source:** Open Google Calendar -> Settings -> Click your specific calendar -> Integrate calendar -> Secret address in iCal format.
   - **Value:** The `https://.../basic.ics` URL from the Secret address field.
   - **Important:** Do NOT use the Public address (`/public/basic.ics`). A non-public calendar will return a 404 for the public path, which will silently skip calendar imports during rollover.

*(Note: `SESSION_SECRET` will be automatically generated by Render during the initial blueprint sync. The Render runtime automatically injects `RENDER_GIT_COMMIT` for Docker services, which the app will use to label the build.)*

## Triggering the First Deploy

Once the environment variables are saved in the Render dashboard, click **Manual Deploy -> Deploy latest commit**.

### 1. Expected First-Deploy Log Output
When the deployment boots, your logs should look exactly like this:
```text
==> Running 'node dist/db/migrate.js && npm start'
Running migrations...
Migrations complete.
> satori@1.0.0 start /opt/render/project/src
> node dist/server/index.js

Initializing database client...
⚡ SATORI server running at http://0.0.0.0:8080
```
*(You will likely see standard npm/node startup logs preceding this, but the Drizzle migrations output must appear first, followed by the successful fastify startup).*

### 2. Failure Modes to Watch For
- **`Error: URL scheme must be "libsql:", "file:"...`**: `TURSO_DATABASE_URL` is missing or typed incorrectly.
- **`ClientError: Unauthorized` or `Invalid token`**: `TURSO_AUTH_TOKEN` is missing, expired, or invalid.
- **`Error: Update failed` or `Table tasks not found`**: The `dist/db/migrations` folder wasn't copied, or the pre-start migration script crashed.

### 3. Post-Deploy Verification
- **Health & Git SHA**: Visit `https://your-render-url.onrender.com/health`. Verify `build.gitSha` matches the commit hash you deployed.
- **Database Status**: Visit `https://your-render-url.onrender.com/health/ready`. Verify `status: ok` to confirm Turso connectivity.
- **Secure Cookies**: Login at `/`. Open dev tools (Application -> Cookies). Verify the `sessionId` cookie has the `Secure` flag checked (this confirms `NODE_ENV=production` is active and enforcing HTTPS).

### 4. Free-Tier Cold Starts
Because this service runs on Render's Free tier, the container will spin down after 15 minutes of inactivity. The next time you open the app, you will see the Matrix-style terminal loading screen for roughly 30–50 seconds while Render spins up the container and executes migrations. This is expected behavior, not a broken deploy.

## Testing Timezone Independence
Satori's calendar recurrence expansion is extremely sensitive to process timezones. A single timezone drift bug can cause events to land on the wrong day depending on the server's local configuration.

To guarantee no drift has been introduced, you must run the calendar test suite under both the production timezone (`America/Chicago`) AND a neutral timezone (`UTC`). Two scripts are provided in `package.json` for this purpose:
- `npm run test` (locked to `TZ=UTC`)
- `npm run test:tz-chicago` (locked to `TZ=America/Chicago`)

Before any deployment involving calendar logic, verify both scripts pass.
